Container-only shared swarm workbench. Read docs {"name":"swarm"} for typed API examples and limits. Which container: the container the coordinator was spawned into — the host master names it with spawn {"container":{"mode":"new","container_config":"<name>"}} (container true = this repo's standard config when one exists — no global default overrides it; run quecto container init first if the roster shows none; agent_cmd get_container_configs lists names); the coordinator spawns workers with container omitted. Only the official isolated-PID adapter (scripts/container-runtime/docker) can host a swarm; host-local reference scripts cannot host a swarm, nor can the host. Default Python RLIMIT_NPROC=1 restricts subprocesses; use the bash tool for Git/tests/external commands under its policy, Python for in-process work/board coordination. Do not raise limits from agent code. Workflow is unavailable for every swarm agent: never set workflow, workflow_guards or workflow_spec on worker launches; an agent running a workflow (guards, bound spec or selected template) cannot create a run; after creation the workflow tool refuses. Ordinary containers that never create a run keep workflow. First op=create a run: goal, constraints, criteria [{id,kind:command|review,description}], member_limit 1–25 incl. coordinator, deadline_in_seconds ≤7 days; then op=run. Then establish a fixed pool with existing spawn/agent_cmd. Idle and reserved members count. Never launch nested containers to reset the cap.
Use op=run with exactly one of code/path. Packaged Python: `from swarm import board`; SQLite persists between fresh executions. board.summary(), task_create(request:str,title:str,acceptance:list[str],dependencies:list[int]), task(id), dependencies(id,ids), claim(id), block(id,token,reason), submit(id,token,evidence), release(id,token), reserve(id,token,paths), release_files(id,token,reservation), send(request:str,recipient:str,body:str,revision:str=None,supersedes:int=None), withdraw(message_id), inbox(), ack(message_id). A message may name its revision and supersede your own earlier unread message to the same recipient; superseded and withdrawn messages leave the inbox, wake nobody, and stay in the audit. evidence(criterion,artifact,revision,kind,passed:bool) records a proposal from workers with accepted=0; only coordinator passed=True accepts it. Evidence entries require artifact and revision. Messages are accepted, then consumed, never implicitly work-completed. Any member may message any other member directly; a question about a task you depend on belongs with that task's owner, not the coordinator. task(id), tasks() and summary tasks carry, for a claimed, blocked or submitted task, owner_last_activity (seconds since the owner's last board event) and owner_state: active or idle (a live member; idle means no board event for 300 s, a prompt to look, not proof of a stall), reserved (admitted, never launched), lost (its harness loss was recorded; resume the run, then revoke), dead (its launcher's harness confirmed the exit) or unknown. An active or idle owner is named as a send recipient (contact: board.send(request, '<owner id>', body)); any other owner has contact null and a recovery note (recover/revoke). A provider suspension is not visible on the board: read it from agent_cmd status. summary counts carry members_without_claim and members_dead; summary(since=cursor) returns a full summary when an owner turned idle by clock alone since that cursor, and next_liveness_check_at says when the next owner would. Use stable member IDs from summary. Large content goes in artifacts.
Coordinator only: amend(goal,constraints,criteria,reason), verify_task(id,token,revision), revalidate_task(id,revision,fresh_evidence) for completed work after later revisions, revoke(id,reason) to take a claim back from a member that will not finish (the task returns to ready, its reservations go, the previous owner is messaged), recover(id, release_files=False) once a member's death is confirmed (its tasks show blocker "worker death confirmed; coordinator recovery required"; after an abrupt exit the blocker adds "reservations retained" because orphaned tool processes may still write the reserved paths, and only revoke or recover(id, release_files=True) frees them), complete(revision), stop(status,reason). revoke and recover need a running run: resume a paused run first. Worker evidence is submitted for coordinator review, immutable under that claim token; identical submit retries are safe. To change submitted evidence, release and reclaim for a new token; do not block a submitted task. Amendments retain full before/after contracts. Empty queues and submitted work do not prove completion: check artifacts and independent review before accepting evidence at the current revision. Only the designated integrator changes branches, commits, or integrates the shared checkout.
Reservations and helper ownership are cooperative (Bash/arbitrary Python can bypass them). Never edit the store or call underscore lifecycle methods. A member you launched that exits (on its own or by your agent_cmd kill) is confirmed dead by your harness: the run keeps running, its tasks block for recover, its reservations are released. Use op=reconcile to observe a vanished harness; only its launcher (or anyone, once that launcher is dead) records the loss, after a ten-second grace in which the launcher's reaper normally confirms the death. A recorded loss pauses the run holding failed, once per member, and retains ownership (revoke reassigns after the master resumes); op=summary for partial progress, op=cancel_run for parent cancellation. On a wake hint, first use op=summary. If terminal, do not execute Python for inbox/ack; report the summary and remain available for supervisor requests/artifact export. When running but no work is ready, yield the turn; existing lifecycle notifications are wake hints, the durable inbox is authoritative. Terminal settlement cancels all Python, the coordinator's included: persist final evidence before complete/stop and report from the harness afterward. Artifact retention is per tool instance; export required evidence before cleanup. Python background jobs use status/output/cancel by job_id. Child processes end with their Python invocation (timeout/drop included); background mode does not detach them. If policy permits subprocesses, wait/join children whose work must finish. Only a wall-clock run budget is enforced; no exact token cap.
Example: {"op":"run","code":"from swarm import board; print(board.summary())"}. Summary shows the first 50 tasks/files with totals; page with board.tasks(offset,limit) / board.file_owners(offset,limit).

Awaiting master clarification/approval: keep the run running, board.block the affected tasks, report the precise question to the master and yield the turn. Do not board.stop("blocked", ...) to wait for one task: stop and complete end the run as a pause only the master (agent_cmd swarm_control resume/close) can lift; members cannot resume it. On a master reply, acknowledge the decision and act on it before optional inbox work; keep the claim token and submit after the approved work. The master uses agent_cmd prompt (idle) or steer (busy); transport acceptance is not a coordinator acknowledgment. The deadline keeps running while awaiting input. Never pause the run because one member failed: pause is a whole-run wait admitting no inference. A member suspended by a provider failure re-arms when the run is resumed or on an explicit agent_cmd steer/follow_up to it; agent_cmd set_model moves it off a failing provider. A member that still will not finish its claim (silent, hung, suspended) keeps it until you revoke(id, reason): revoke, let another member claim, and continue integration.

Bash build/test commands do not inherit swarm launch identity; use managed spawn for participating agents. Wake hints are checked against board state when sent but may be stale on arrival. Accepted steering outranks buffered idle work. A control acceptance response means queued, not acted upon; verify handling in the correlated response and transcript.
