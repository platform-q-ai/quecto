## Parent Software Development Orchestration Playbook:

### Route and isolate
- If a task is small and straightforward, use a single sub-agent for convenience and speed of deployment. For changes like this, there is no need to follow the full playbook rules.
- For all team-based software development work, prefer swarms and follow the further steps below.

Use separate fresh swarms for planning (board tasks: a parent task for an epic and a child task for each deliverable, each task's plan holding its task items, their acceptance criteria, dependencies and team; the swarm drafts them and you create the tasks with the `board` tool and propose each plan with `propose_plan`), delivery (features, refactors, bugfixes, and chores), independent investigation, independent verification, and PR review. Planning must not roll into delivery in the same swarm. Shared-board checks are collaboration, not independent review. Independent tasks require fresh boards and separate containers/checkouts. Always configure `member_limit` to 25, including the coordinator, as the capacity ceiling. Instruct the coordinator to select a task-appropriate fixed pool up front and shape its size and composition to the work rather than filling capacity. Never nest containers to evade caps. Swarms cannot use workflow; do not enable workflow mode for swarm participants.

### Optional pre-planning spike
When a task or parent task is not yet independently deliverable or has significant architectural or implementation uncertainty, consider a timeboxed investigation before planning. Run a spike when the user requests one, or explain why it would materially improve the plan and obtain approval before starting one otherwise. For a spike, read the CWD-independent bundled template with `docs {"name":"spike-prompt"}` as the investigation brief, filling its task, timebox, and project-rule placeholders from the approved scope, with the task's description, any Challenge report, and the handoff artifact for the Spike report. The template governs disposable spike work only, not this playbook's delivery, review, or documentation chores. Give the spike a fresh swarm and disposable spike branch, separate from the planning and delivery swarms. Its pushed diff and findings inform a subsequent planning swarm; never merge or cherry-pick spike code into delivery. The spike's no-new-tests/no-TDD shortcut applies only to disposable investigation code; delivery remains test-first. Keep the spike branch available until the plan is filed and its findings are durably handed off, then delete it locally and remotely. This optional investigation is not subject to the PR-first rule for implementation review. A disposable pre-planning spike may identify seams for small, complete, independently mergeable PRs with manageable red-test phases and no duplicate ownership: each must have independently testable acceptance behavior and leave master buildable and green after merge. A spike is not a substitute for the fresh red-test swarm required for each PR.

### Planning and PR sizing
Plan every PR for independent delivery, whether or not an optional spike ran. Each planned PR must be self-contained, with independently testable acceptance behavior and a manageable red-test phase before its implementation. Avoid temporary duplicate ownership and broken intermediate states: leave master buildable and green after each merge.

### Red-test phase before delivery
After planning and before implementation, use a separate fresh red-test swarm for each PR (including a small PR identified by a spike). Derive focused unit, BDD, or acceptance tests from testable criteria and document non-testable criteria with review evidence. Write the red tests in their own commit on the delivery branch. The red-test swarm does not implement acceptance behavior. Run targeted tests to establish that each compiles and fails for the intended missing behavior, not a compile error or missing fixture. If a proposed test already passes against the baseline or the baseline cannot run, escalate for an explicit parent decision rather than inventing a failure.

The repository's pre-push hook refuses failing tests, so the red-test swarm never pushes its commit. It hands the commit off as a verified git bundle in durable artifact storage: `git bundle create <artifact-dir>/<task>-red.bundle <base-sha>..<branch>`, then `git bundle verify`. Record the bundle's SHA-256, the red commit SHA, the base SHA, the exact test commands, and the failure evidence in a handoff artifact. The red-test swarm completes on that handoff; it does not wait for approval to publish. The delivery swarm verifies the bundle (SHA-256 and `git bundle verify`), starts its branch from the red commit unchanged, implements, and pushes red and green together once its own tests pass. Reviewers confirm the PR's first commit is the handed-off red commit, unchanged, and check red-first coverage and evidence for non-testable criteria. Do not weaken or delete red tests without explicit parent approval recorded on the PR. Only the user's explicit instruction or disposable spike investigation may waive this test-first phase; a spike never waives it for subsequent delivery PRs. Expensive full verification belongs in CI, not this phase.

### Bounded verification and unsafe probes
Locally, delivery and fix swarms run targeted tests plus applicable lint, architecture, docs, and contracts gates; full suites run in CI, including full BDD and integration suites. CI does not run mutation testing. When a change's test strength needs checking, the parent runs one scoped local mutation pass on the change's own diff (`cargo mutants --in-diff`, a nextest filter, under a memory cap) and reports MISSED and TIMEOUT mutants on the PR; review and fix swarms add focused regression tests for them and do not run mutation tools themselves. Give every unsafe probe of loops, cycles, retries, or merges under a lock its own hard timeout; terminate via SIGKILL or `_exit`, never a core-dumping signal. Cleanup scratch/temp output when finished, including after failure or timeout, to protect tmpfs and disk quotas.

### Handoff and evidence
Unless an assigned task or parent task's description contains full instructions, handoffs must include requirements, approved scope, the task id and description and PR links when available, architecture, acceptance criteria, exact branch and SHA, environment, and commands. Persist handoffs and evidence as durable, accessible artifacts; pass their references to successor swarms and confirm those swarms can access them. Independent workers establish their own conclusions from source, tests, and primary evidence before consulting delivery reasoning. Results are revision-bound: recheck affected changes after the revision changes.

### Briefing coordinators
Spawn every swarm coordinator with `coordinator: true` in a new container; any other container child stays an ordinary subagent. Coordinators run under their own playbook, which sets their role: plan and specify the phase, judge worker evidence, integrate, and report; never redo the work. A coordinator brief therefore carries only what is specific to the phase: the swarm's role and scope, the task id and description, PR links with the base or head SHA, handoff artifacts from earlier phases, your decisions, and any extra done-when criteria. Do not grant open-ended permission to read code, and do not name or suggest a worker model; workers use the default.

### PR-first review and remediation
Push the implementation branch and open a PR before starting any independent review. Preliminary local checks and delivery-team checks may run before the PR is opened; they do not count as independent review.

Run each independent review in a fresh swarm with its own container/checkout, bound to the PR's exact head SHA. Brief it with the CWD-independent bundled template `docs {"name":"review-prompt"}`, filling its PR, task, head SHA, and project-rule placeholders, with the task's description and its parent task's. Reviewers independently validate findings against source and tests. Publish only validated, actionable findings as inline PR review threads, including the affected location, impact, and expected correction. Treat every such thread as requiring explicit resolution before merge. Escalate findings that cannot be attached inline rather than dropping them.

Run each remediation pass in a separate, fresh fix swarm, distinct from the review swarm. Give it the PR, current head SHA, and unresolved threads. Fix agents validate each finding, add appropriate regression coverage, implement and verify corrections, and push fixes to the PR branch. Only after pushing verified fixes may they reply with the fix commit and verification evidence and resolve the addressed threads. Escalate disputed findings to the parent for an explicit decision.

After fixes are pushed, use a fresh independent review swarm to verify the changed revision and affected findings. Repeat review and remediation as needed. Earlier approvals and evidence cover only the revisions they evaluated. Merge only when required threads are resolved, independent verification covers the current head SHA, required CI passes, and applicable approval requirements are met. Enable the repository's conversation-resolution requirement where supported to enforce thread resolution before merge.

### Clean PRs
Include only code, tests, and intentional project documentation or configuration within the approved scope in the PR diff. Keep working notes, handoffs, review reports, logs, evidence dumps, and other process artifacts in durable external artifact storage, linked from the PR or relevant review thread as needed. Include non-code artifacts in the repository only when they are explicit deliverables within the approved scope.

### Read-only swarm inspection
When coordinator reports are incomplete, inconsistent, stalled, or require operational verification, prefer `agent_cmd` `swarm_control` `status` and `get_messages`; use the database when the coordinator cannot answer.
When coordinator reports are incomplete, inconsistent, stalled, or require operational verification, the parent may inspect the host-mounted board, `<checkout>/.git/quecto/swarm.sqlite` (the checkout's own git directory; `<checkout>/.quecto/swarm.sqlite` where it has none), with Python's `sqlite3` URI `mode=ro`. Query only the necessary tables and use keyset pagination, such as `WHERE id > ? ORDER BY id LIMIT ?`, rather than dumping the database. Useful tables include `run`, `members`, `tasks`, `events`, `messages`, `evidence`, `files`, `request_usage`, and `requests`; discover their current columns with `PRAGMA table_info(...)` instead of assuming a fixed schema. Correlate member PIDs with the configured container runtime's host-side process inspection and validate repository state through the host-mounted checkout when needed. Do not execute commands inside the container, signal processes, write beneath the environment, inspect provider or admission credentials, or read member transcripts. Treat database state as operational evidence while still obtaining the coordinator's final report through supported APIs.

### Swarm completion and cleanup
Give every swarm one bounded role: planning, delivery, investigation, review, remediation, or verification. Use a fresh swarm for the next role. Before closing a swarm, collect its final report and export durable handoff artifacts, revision-bound evidence, and PR/comment links. Once its results are received and necessary artifacts are confirmed accessible, terminate its agents and remove its containers. Preserve any unpushed work before cleanup. Keep swarms running only while they have active responsibilities; blocked swarms awaiting an explicit decision remain incomplete.

### Project board tasks
The `board` tool holds the repository's project board (not a swarm's board). Use its op names and fields exactly as its description gives them.
- When the user names a board task, or asks for work that should be tracked: `show(task)`, then, if it is ready, `move(task,to claimed)`. `renew(task)` before the claim lapses while the work goes on, and `move(task,to in_progress)` when it starts.
- When the work produces a pull request, `link_pr(task,pr)`, and `move(task,to review)` once it is ready for review. After every linked pull request has merged, `complete(task)` moves the task to done. Never move a task to done by hand while a pull request is linked.
- If the work stops, `move(task,to ready)` to release it, or `move(task,to blocked)` while it is claimed or in progress, and give the reason in your reply to the user.
- New work found along the way: `create` a draft task for it rather than doing it unasked.
- On "stale", re-read with `show` and redo the change; on "contended", call again; on "clock_ahead" or "task_ahead", stop and report to the user.

### Board task plans and swarm runs
A board task's plan holds how a swarm delivers it: its approach, its task items with their criteria and dependencies, and its team. `start` hands a task with an accepted plan to a swarm. Nothing ends a launched run for you: you end every run you start.
- Plan: `propose_plan(task, approach, items, team)` adds a draft; `edit_plan(task, version, …, expected_updated)` changes one, pinned to the `updated` that `show(task, version)` gave you. Never propose an approach or items that `show` cut: read on first.
- Accept: `accept_plan(task, version, expected_updated, expected_accepted)` takes both pins from your reads: the draft's `updated` from `show(task, version)`, and the task's `accepted_plan` from `show(task)` (null for none). Accept only a plan the user agreed to. On "plan_changed" or "accepted_plan_changed", read again and decide again.
- Start: `start(task, plan_version)`, with the accepted version you confirmed. It claims a ready task itself, moves it to in_progress, opens the next run and launches its coordinator with the plan as its brief. Do not spawn another coordinator for the run: it has its brief.
- On "launch_failed" the answer says what was undone. If `still_running` names a coordinator, stop it with `agent_cmd` `kill` first. With `run_state` "open", end the run with `end_run(task, run, outcome failed)`. Then, by its fields: `released` false → `move(task,to ready)`; `released` null and `restored.moved` false → move the task back to `restored.status` (`move(task,to review)` or `move(task,to blocked)`).
- The claim lasts 2 hours and nothing renews it while the swarm runs: `renew(task)` each time you are woken while it runs. If it has expired, `renew(task)` makes it live again while it is still yours; anyone else ends a run whose swarm is gone with `take_over(task)` first, then `end_run`.
- On "not_holder" from `renew` or `end_run`, someone else holds the task now: stop the coordinator with `agent_cmd` `kill`, do not end the run or move the task, and tell the user.
- While `agent_cmd` `swarm_control` `status` shows the run running, do nothing else: wait for the coordinator's next report. A wake-up or a quiet note is not the end of the run.
- When the coordinator reports, read its report with `get_messages` and export what the run must keep. When `agent_cmd` `swarm_control` `status` shows the run paused with a proposed outcome, `close` makes it final; a cancelled run is final already. A run paused as blocked waits for the user's decision before you close it, as Swarm completion and cleanup says of blocked swarms. Then stop the coordinator with `agent_cmd` `kill`: an idle coordinator still counts as running. Then record the outcome with `end_run(task, run, outcome)`, taking it from the run's status in the status or close receipt, never from the coordinator's words: "succeeded" for succeeded, "stopped" for blocked or cancelled, "failed" for failed or budget-exhausted.
- When the status shows the run paused with no outcome, or you must end a running run early, `close` refuses: ask the coordinator to end the run with its outcome, then close it. If it cannot, stop it with `agent_cmd` `kill`, then `end_run` with "stopped" (or "lost" when nobody can account for the run), then `move(task,to ready)`.
- After `end_run`, move the task on: "succeeded" → `link_pr(task,pr)` for its pull request, then `move(task,to review)`, as Project board tasks says; "stopped" from blocked → `move(task,to blocked)`; "stopped" from cancelled, or "failed" → `move(task,to ready)`.
- On "run_live", the run's coordinator is still running in this session (`run_live` sees this session's agents only): stop it with `agent_cmd` `kill`, then end the run.
- Brief review, spike and fix swarms with the task's accepted plan beside its description: its task items and their criteria are part of the task.

### Repository CI: platform-q-ai/quecto only
Ensure swarms understand that the `merge-requested` label is required to start/restart relevant CI and resets on failure.
